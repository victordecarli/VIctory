# VIctory-32

A fork of [VIctory](https://github.com/Marvisak/VIctory) that runs Grand
Theft Auto VI (Xbox Series X|S) natively on Windows, from files the user
supplies. It has two aims: running on GPUs whose waves have 32 lanes
(NVIDIA and others), where the console's have 64, and keeping the code that
title code calls safe, with numbers produced by commands rather than typed
by hand.

**This repository contains no game files, code or assets.** You need your
own copy of the game (`docs/asset-policy.md`). It is not affiliated with or
endorsed by the game's developer or publisher.

The title's x86-64 code runs unchanged inside our process; VIctory supplies
the platform underneath it and converts the title's data, ahead of time where
it can and on first use where it must (shaders). See
[docs/architecture.md](docs/architecture.md).

Upstream: this fork follows [Marvisak/VIctory](https://github.com/Marvisak/VIctory)
`main` up to `ffe310e` (2026-11-24). Upstream has moved on since; its own
README describes where it is now.

## Status

**Not playable yet.** The title boots, runs its menus at its own 30 fps and
loads the world, where rendering fails. This is what upstream reported on
2026-11-23 for the code this fork is based on; the fork's changes have not
been run through the game since.

| Stage | State |
|-------|-------|
| Boot, first-boot screens (accessibility, language, settings, legal) | works, 30 fps |
| Intro video with sound | works |
| Start screen, profile and saves | works |
| Loading into the world (about 50 s) | works |
| The world (first mission's intro) | reached and runs with indirect draws; its title card renders, the scene after it is still dark; 0.5-1.8 s per frame |

Tested upstream on one machine: Windows 11, AMD RX 6700 XT.

> **Warning.** Entering the world on a real GPU can currently hang it, and
> Windows then resets the display driver (every monitor goes black for a
> moment). To look further, use a diagnostics build with
> `VICTORY_D3D12_WARP=1`, which renders on the software adapter.

What each part does today and what it still needs:

| Subsystem | Today | Needs |
|-----------|-------|-------|

## What VIctory-32 adds

GPUs with 32-lane waves ([#47](https://github.com/victordecarli/VIctory/issues/47)):
- With more than one GPU, the title runs on the highest-performance one and
  the log names it (`97a9a0a`).
- The log names the host's wave lane range, and each translation carries
  the wave size it needs; `translate --host-lanes 32` translates for such a
  GPU and counts the compute programs that still need 64 lanes (`79896c2`,
  `61557e4`, [#58](https://github.com/victordecarli/VIctory/pull/58)).
- Console 64-lane compute runs as two 32-lane waves where the result is
  exact (`e8aafeb`, `1b589d8`, [#60](https://github.com/victordecarli/VIctory/pull/60)).
  So do programs whose LDS accesses every lane runs (with a group barrier
  before each), and programs that write a scalar in a lane branch and do
  not read it past that branch (`f09e903`,
  [#63](https://github.com/victordecarli/VIctory/pull/63)).
  The [Shader translation](#shader-translation) block is measured for a
  32-lane GPU.

Safe to call from title code:
- No `unwrap` or `expect` outside tests (`5913d19`); the panics that title
  code could reach in the bitcode writer, the HLE host exports and the GPU
  stages return the API's failure instead (`a1c63b8`, `13bec12`, `c4ae7c1`,
  `a2db8c8`, `197bf80`, `cab9fcf`).
- FFI functions that dereference raw pointers are `unsafe` with a `# Safety`
  section, one module at a time; 3 module-level `not_unsafe_ptr_arg_deref`
  allows remain (see the lint ratchet in `AGENTS.md`).
- A pointer read goes through `NonNull` instead of a null check
  (`c8753f8`); tests check the pointers a call wrote out before using them
  (`c26b43d`, `cc0ba34`).
- Device-removed reports say whether `VICTORY_D3D12_DRED` was on (`ddccc9a`).

Measured, not guessed:
- `cargo xtask progress` writes the [Shader translation](#shader-translation)
  block from `victory translate --json`; a test fails when the two disagree.
- `cargo xtask audit-metrics` counts and grades every crate (`61ddbe3`,
  `135aa2a`).
- `cargo xtask wincheck` type-checks and lints the Windows code from any host,
  in CI (`9b8509c`, `5f2ca69`).
- `AGENTS.md` is the contract for every change; `cargo xtask citations` fails
  when a path it cites is gone (`2f1d505`).

## Getting started

Requirements: Windows 10/11 x64, a CPU with AVX2, a Direct3D 12 GPU with
shader model 6.6 (and mesh shaders for the world), Rust (pinned in
`rust-toolchain.toml`). With more than one GPU, the title runs on the
highest-performance hardware one (DXGI's order: external, discrete, then
integrated); the log names it at start-up (`host device adapter`).

The title also needs several GiB of available Windows commit at startup.
Check **Committed** under **Task Manager → Performance → Memory**. If
`crashes.log` reports Windows error 1455, close other applications or increase
the Windows paging file size, then retry.

```powershell
cargo xtask install-hooks                # asset-policy check on every commit
copy victory.example.toml victory.toml   # then set your paths (outside the repo)
cargo test --workspace                   # needs no game data
cargo run -p victory -- config           # check your paths
```

Run the title:

```powershell
cargo build --release -p victory
target\release\victory.exe run --execute
```

Without a path, `run` starts the only `.exe` at the top of the configured
`game_dir`; give the executable's path to run another. Run it from the
repository root, where `victory.toml` is.

For tests, `scripts\run.ps1` does all of that. It builds the diag build
(see [Debugging](#debugging); `-Release` for the one above), runs the title
from the repository root with only the switches it is given (`-Warp`,
`-GpuDebug`, `-Gbv`, `-Log <filter>`, `-Keys <keys>`, `-Env @{ NAME =
'value' }`), leaving the session's `VICTORY_*` switches out of the run
unless `-KeepEnv`, and when the title ends shows the run log's summary:
the last frame report, the costliest dropped draws and a crash.
`scripts\run-summary.ps1` shows the newest run again;
`Get-Help scripts\run.ps1 -Full` lists every option.

```powershell
scripts\run.ps1 -Warp                       # software adapter: enters the world without a GPU hang
scripts\run.ps1 -GpuDebug -Log 'victory_gpu=debug,info'
```

The window caption shows the framerate. Saves, settings and `crashes.log`
are kept under the data folder (default `%LOCALAPPDATA%\victory\data`), derived
data under the cache folder, run logs under the log folder (see Logging).

Input: XInput pads. With none connected the keyboard is a pad while the
title's window has focus:

| Keys | Pad |
|------|-----|
| W A S D / I J K L | left / right stick |
| arrows | D-pad |
| Enter, Backspace, X, Y | A, B, X, Y |
| Q / E, Z / C | shoulders, triggers |
| F / H | stick clicks |
| Esc, Tab | Menu, View |

## Commands

```
victory inspect <exe|dll> [--imports] [--exports]
victory census [paths...] [--missing] [--strict]
victory lib-exports <import.lib> [--list]
victory shader-info [paths...] [--verbose] [--disasm]
victory translate [paths...] [--validate] [--pipelines] [--list] [--jobs N] [--host-lanes N]
                  [--json <file>]
victory run [exe] [--execute] [--unimplemented trap|zero] [--strict]
            [--console series-x|series-s] [-- <title arguments>]
victory config
```

`victory translate` exits 1 when it could not measure everything it was
given: an unreadable file, a failed directory walk or a panic in a program
each count as an infrastructure failure and are listed at the end. Files
above 2 GiB are not read and are not failures: they are logged and counted
in the `files` line. Shaders the translator cannot handle yet do not change
the exit code. `--json <file>` (with `--validate`) also writes the counts per
kind of program (found, and validated: emitted as DXIL the validator
accepts; for compute, how many of those need 64-lane waves), aggregate
numbers only; `cargo xtask progress --record <file>` turns
them into the [Shader translation](#shader-translation) block.

`victory translate` also reads:

| Variable | Effect |
|----------|--------|
| `VICTORY_DXIL=<path>` | the `dxil.dll` that `--validate` loads (default: the newest one under `C:\Program Files (x86)\Windows Kits\10\bin`) |
| `VICTORY_EMIT_DUMP=<dir>` | writes there, with `--validate`, the first 3 shaders failing with each validator error (`.dxil`, and `.txt` with the error); with `--list`, every emitted shader |
| `VICTORY_PAIRS=<vs>+<ps>,...` | after the walk, creates a pipeline on the GPU for each pair; each side names a shader by part of its label (file and stage, as `--list` prints it) |

Logging: `VICTORY_LOG=victory_loader=trace,info` (a release build logs
info and above; a filter that does not parse is reported and replaced by
`info`). `victory run` also writes each process's log (a relaunch and the
audio recorder are processes of their own) to
`<log_dir>/run-<UTC time>-<pid>.jsonl` (`log_dir`: `VICTORY_LOG_DIR` or
`[paths].log_dir`, default `%LOCALAPPDATA%\victory\logs`; `victory config`
prints it), keeping the newest 20: one
JSON object per line, the event's fields beside `timestamp` (UTC),
`level`, `target`, `threadId` and `threadName`. The console's first line
names the file. A process names the other's id in both logs: a relaunch
in `run_start` (`previous_pid`) and the old process's `relaunched` line,
the audio recorder in `run_start` (`parent_pid`) and its parent's
`audio capture started` line. Events with the target `victory::summary`
are logged whatever the filter: `run_start` (the BLAKE3 of `victory.exe`,
the arguments and every `VICTORY_*` variable), the title's build, DLLs and
missing imports, the host adapter and its wave lanes, the frame reports
(`"frame report"` every 5 s: per frame over every frame since the last
one, `fps`, `ms_per_frame`, `cpu_ms` preparing submissions with its
`copies_ms`/`copies_mb` and `textures_ms`/`textures_mb`, `gpu_ms`
waiting for the GPU, `copy_back_ms`/`copy_back_mb`, `draws_per_frame`,
`dropped_per_frame`, `indirect_per_frame`; `pipelines_making` now; and
the `frame` the drop lines also name), the draws the host did not run, and a crash
(`"message":"crash"`, the report in `report`), which also goes to
`crashes.log` as before. A dropped draw is counted where its cause lives,
in every build: on the shader that does not translate (with the
translator's error and its `class`), on the pipeline still being made,
refused by the host or not prepared, or by a general `cause` (no pipeline
set, indirect arguments the host cannot read, a dispatch with a graphics
pipeline, an indirect mesh dispatch). Each shader, pipeline and
cause logs a `"first drop"` line once, and each frame report is followed
by `"drop totals"` and the run's totals for the 40 costliest of each.
A case the host skips or does not implement yet logs one `warn` line the
first time; every case after it is counted, and each frame report is also
followed by a `"warning total"` line for each such warning that had new
cases since the previous report (`site`, `message`, `detail` when the
warning is about one object or slot, `total` for the run, `since_last`,
`frame`).
For example, with `jq`:
`jq -c 'select(.target == "victory::summary")' run-*.jsonl`.

## Debugging

A release build has no debugging aids. Build them in with

```powershell
cargo build --profile diag -p victory --features diagnostics   # target\diag\victory.exe
```

| Variable | Effect |
|----------|--------|
| `VICTORY_LOG=<target>=debug,...` | debug and trace output |
| `VICTORY_STACKS=20,60` | every thread's stack at those seconds |
| `VICTORY_WATCH=<rva>,...` | logs a title u32 when it changes |
| `VICTORY_KEYS=30:Enter,35:X` | presses keys at those seconds, focus or not |
| `VICTORY_CRASH_SAVE=<rva>:<len>,...` | saves title memory to the cache folder on a crash |
| `VICTORY_CAPTURE=<dir>` | saves presented frames (powers of two, or `VICTORY_CAPTURE_FRAMES=<list>`) |
| `VICTORY_DUMP_TARGETS=1` | with the two above, saves every render target of those frames |
| `VICTORY_COPY_MODE=plain\|none` | for timing copies of title memory to the host: `plain` copies directly instead of through the kernel (an unmapped source page then crashes), `none` skips them (frames come out wrong) |
| `VICTORY_D3D12_DEBUG=1` | host debug layer: names the command of an invalid call |
| `VICTORY_D3D12_GBV=1` | with the above, GPU-based validation (bad descriptor use reported, not faulted; slow) |
| `VICTORY_D3D12_DRED=1` | on a GPU failure (hang, page fault), the allocation hit and the commands in flight; without it the report says DRED is off |
| `VICTORY_SKIP_PIPELINES=<hash>,...` | omit draws and dispatches, including indirect ones, whose pipeline contains a listed 16-digit shader hash |
| `VICTORY_GPU_TIMING=1` | with the above, each list of a submission run and timed on its own; slow lists logged with their slowest commands |
| `VICTORY_D3D12_WARP=1` | host device on the software adapter (slow; cannot reset the driver) |
| `VICTORY_SHADER_LOOP_LIMIT=<n>` | translated shader loops stop after `n` iterations per lane instead of 2^20 (own shader cache entries); if a lower `n` makes world frames much faster, loops hitting the limit are what makes them slow |
| `VICTORY_AUDIO_CAPTURE=<file.wav>` | records what the title plays (our process only) |
| `VICTORY_XMA_DUMP=<dir>` | saves the first 32 XMA voices' context and input |

Every build appends crashes and host GPU failures to `crashes.log` in the
title's data folder.
